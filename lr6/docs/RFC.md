# RFC: консольный клиент PostgreSQL для лабораторной работы № 6

## Статус

Предлагается к реализации.

Основание: [задание лабораторной работы](task.pdf).

## 1. Контекст

Лабораторная работа требует консольное приложение из десяти пунктов,
демонстрирующих основные способы доступа к реляционной базе. Приложение
работает с базой PostgreSQL 17 `supply_lab`, созданной в `lr1`, и использует
функции и процедуры из `lr3`.

Согласно `NOTES.md`, для ЛР 6 применяется raw SQL. Клиент пишется на Python 3
с драйвером `psycopg`; SQLAlchemy, ORM и конструкторы запросов запрещены.

## 2. Архитектура

Приложение состоит из трёх частей:

- `db.py` открывает соединение по стандартным переменным PostgreSQL;
- `queries.py` содержит десять независимых функций с SQL и преобразованием
  результата в простые структуры Python;
- `cli.py` показывает меню, проверяет пользовательский ввод и печатает
  табличный результат.

Вся фильтрация, соединения, группировка, оконные вычисления, DDL и DML
выполняются PostgreSQL. Python не имитирует запросы обходами коллекций.
Пользовательские значения передаются через `%s`; строковая интерполяция SQL
не используется.

## 3. Контракт подключения и транзакций

По умолчанию используются:

- `PGHOST=127.0.0.1`;
- `PGPORT=55432`;
- `PGDATABASE=supply_lab`;
- `PGUSER=postgres`;
- `PGPASSWORD=postgres`.

Переопределение выполняется стандартными переменными окружения. Пароль в
исходный код не встраивается. Соединение работает с `autocommit=True`, а
изменения выполняются внутри `connection.transaction()`. На старте приложение выполняет
`SELECT current_database(), current_user` и отказывается работать не с базой
`supply_lab`.

Читающие пункты не оставляют долгоживущую транзакцию. DDL и DML фиксируются
только после успешного выхода из явного транзакционного блока. При ошибке блок
откатывается, соединение остаётся пригодным для следующего пункта меню.

## 4. Десять функций меню

### 4.1. Скалярный запрос

`show_delivery_count_by_status(status)` принимает один из статусов
`accepted`, `inspection`, `rejected` и возвращает одно число:

```sql
SELECT count(*)
FROM public.deliveries
WHERE quality_status = %s;
```

### 4.2. Запрос с несколькими JOIN

`show_recent_deliveries(limit)` соединяет `deliveries`, `suppliers`,
`products` и `warehouses`. Результат содержит номер поставки, поставщика,
товар, склад, дату, количество и стоимость партии. Ограничение проверяется в
Python как целое число от 1 до 100 и затем передаётся параметром.

### 4.3. CTE и оконные функции

`show_supplier_cost_rating(date_from, date_to)` использует CTE для расчёта
стоимости поставок по поставщикам за полуинтервал `[date_from, date_to)`, а
затем выводит:

- сумму по поставщику;
- `dense_rank()` по убыванию суммы;
- долю поставщика в общей стоимости через `sum(total_cost) OVER ()`;
- накопительную сумму через оконный `sum(...) OVER (ORDER BY ...)`.

Границы периода передаются как параметры, условие `date_from < date_to`
проверяется до выполнения запроса.

### 4.4. Запрос к метаданным

`describe_columns(table_name)` читает `information_schema.columns` только для
схемы `public`. Допустимые имена выбираются из фиксированного множества
`suppliers`, `products`, `warehouses`, `warehouse_sections`, `deliveries`.
Результат содержит позицию, имя, тип, nullable и default. Имя таблицы также
передаётся параметром, а не вставляется в SQL.

### 4.5. Вызов скалярной функции

`show_delivery_total(delivery_id)` вызывает созданную в ЛР 3 функцию:

```sql
SELECT public.fn_delivery_total(%s);
```

Неизвестный идентификатор должен показать пользователю сообщение PostgreSQL,
после чего приложение откатывает неуспешную транзакцию команды.

### 4.6. Вызов табличной функции

`show_supplier_deliveries(supplier_id)` выполняет:

```sql
SELECT *
FROM public.fn_supplier_deliveries(%s);
```

Пустой результат является корректным и печатается как «строки не найдены».

### 4.7. Вызов хранимой процедуры

`describe_table_with_procedure(table_name)` вызывает процедуру метаданных из
ЛР 3:

```sql
CALL public.sp_describe_table(%s, NULL::jsonb);
```

Значение `INOUT p_metadata` читается из результирующей строки `CALL` и
выводится как форматированный JSON. Это отдельный пункт от прямого запроса к
`information_schema`.

### 4.8. Вызов системной функции

`show_server_info()` выполняет один запрос к системным функциям PostgreSQL:

```sql
SELECT current_database(), session_user, current_schema(), version();
```

### 4.9. Создание таблицы

`create_delivery_notes_table()` последовательно выполняет:

```sql
CREATE SCHEMA IF NOT EXISTS lr6;

CREATE TABLE IF NOT EXISTS lr6.delivery_notes (
    note_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    delivery_id bigint NOT NULL
        REFERENCES public.deliveries (delivery_id),
    note_text text NOT NULL CHECK (btrim(note_text) <> ''),
    created_at timestamp with time zone NOT NULL DEFAULT clock_timestamp(),
    created_by text NOT NULL DEFAULT session_user
);
```

Таблица соответствует предметной области и не меняет структуру объектов
предыдущих лабораторных работ.

### 4.10. Вставка данных

`add_delivery_note(delivery_id, note_text)` вставляет одну запись
параметризованным `INSERT ... RETURNING`. Пустая заметка отклоняется до
запроса, а существование поставки гарантирует внешний ключ. Если пункт 9 ещё
не выполнялся, приложение выводит понятную рекомендацию создать таблицу.

## 5. Интерфейс консоли

Меню содержит пункты `1`-`10`, `0` для выхода и повторяется после каждой
операции. Для ввода используются отдельные функции `read_int`, `read_date`,
`read_choice` и `read_non_empty_text`. Неверный ввод не отправляется в базу и
не завершает процесс.

Результаты печатаются без сторонней библиотеки: заголовки берутся из
`cursor.description`, ширина колонок рассчитывается по строковым значениям.
Для больших результатов действует явный `LIMIT`, а `NULL` отображается как
`NULL`.

Обрабатываются отдельно:

- ошибка соединения при старте;
- нарушение ограничений;
- неизвестная функция или процедура, если ЛР 3 не установлена;
- синтаксическая или серверная ошибка запроса;
- `EOFError` и `KeyboardInterrupt` как штатное завершение.

## 7. Тестирование

Интеграционные тесты написаны на стандартном `unittest` и работают с
реальной `supply_lab`. Перед тестами проверяется наличие
`public.fn_delivery_total`, `public.fn_supplier_deliveries` и
`public.sp_describe_table`; отсутствие зависимости считается ошибкой
окружения, а не пропуском теста.

Тесты DDL/DML используют отдельное соединение и внешнюю транзакцию с итоговым
`ROLLBACK`. Проверяется:

| Пункт | Проверка |
| --- | --- |
| 1 | скаляр равен контрольному `count(*)` |
| 2 | JOIN возвращает согласованные бизнес-идентификаторы четырёх таблиц |
| 3 | ранги не убывают, доли дают 100% с учётом округления |
| 4 | метаданные `deliveries` содержат `delivery_id` и `batch_number` |
| 5 | стоимость равна `quantity * unit_cost`; неизвестный ID даёт ошибку |
| 6 | каждая строка принадлежит выбранному поставщику |
| 7 | JSON процедуры описывает таблицу `deliveries` |
| 8 | имя текущей базы равно `supply_lab` |
| 9 | таблица создаётся повторно без ошибки |
| 10 | заметка вставляется и возвращает `note_id`; неверный FK отклоняется |

Дополнительно тестируется восстановление соединения после ожидаемой ошибки и
отсутствие SQL-инъекции в текстовых параметрах.

Запуск:

```bash
python3 -m unittest lr6/tests/test_queries.py
```

## 8. Критерии готовности

1. В консольном меню доступны ровно десять требуемых операций.
2. Каждая операция реально выполняется на сервере PostgreSQL.
3. Пункты 5-7 используют объекты ЛР 3, а не дублируют их логику в Python.
4. Все пользовательские значения параметризованы.
5. После серверной ошибки приложение продолжает принимать команды.
6. Тесты проходят на чистой `supply_lab` после установки ЛР 3 и не оставляют
   тестовых данных.
