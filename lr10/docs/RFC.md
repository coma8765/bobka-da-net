# RFC: аналитический дашборд поставок в Grafana

Статус: реализовано и проверено через API; визуальная проверка и скриншоты ожидают доступного браузера. Результаты: [RFC-track.md](RFC-track.md), запуск: [README](../README.md).

## 1. Цель и требования

Разработать для лабораторной работы № 10 дашборд «Поставки: стоимость и качество» на данных `supply_lab` из лабораторной работы № 1. Дашборд должен показывать динамику поставок, их стоимость, распределение по складам и результаты приёмки.

Основание: [задание](task.pdf), [описание БД](../../lr1/db/DESC.md), [инструкция lr1](../../lr1/README.md) и CSV из `lr1/data`. В запросе файл задания назван `taask.pdf`; фактическое имя в репозитории — `task.pdf`.

Обязательные требования задания:

- Установить Grafana локально или через Compose.
- Подключить PostgreSQL и получить успешный результат Save & Test.
- Создать уникальный дашборд минимум из пяти панелей.
- Включить таблицу, график и столбовую диаграмму.

RFC определяет решение из шести панелей. Создание конфигурации, запуск Grafana и проверка живой БД относятся к последующей реализации; при подготовке RFC изучены документация БД и данные CSV. SQL-исходники не анализировались ввиду заданных ограничений на анализ кода вне разрешённых корней.

## 2. Исходные данные

По документации используется PostgreSQL 17, база `supply_lab`, контейнер `lr1-postgres`, опубликованный порт `55432` на хосте и порт `5432` внутри контейнера.

| Таблица | Роль | Строк в текущем CSV |
| --- | --- | ---: |
| `suppliers` | Поставщики, ключ `supplier_id` | 1000 |
| `products` | Товары, ключ `product_id` | 1000 |
| `warehouses` | Склады, ключ `warehouse_id` | 1000 |
| `warehouse_sections` | Иерархия секций внутри склада | 3000 |
| `deliveries` | Партии товаров от поставщиков на склады | 5000 |

Одна строка `deliveries` — одна поставка одного товара. Поставка связана с поставщиком, товаром и складом через внешние ключи. Уникальна комбинация `supplier_id`, `product_id`, `warehouse_id`, `batch_number`. Повторяющийся номер партии сам по себе не означает дубликат.

Для аналитики используются `delivered_at`, `quantity`, `unit_cost`, `quality_status` и справочные названия. `delivered_at` имеет тип `timestamp without time zone`; стоимость хранится в `numeric`. Статусы: `accepted`, `inspection`, `rejected`.

В текущем `deliveries.csv`:

- Время поставок: от `2025-01-01 12:25:00` до `2026-09-04 07:53:00`.
- Принято 3019 поставок, на проверке 1008, отклонено 973.
- Сумма `quantity * unit_cost` по всем статусам: `280292140666.85`.

Это контрольные значения CSV, а не результат запроса к работающему PostgreSQL. При изменении набора данных контрольные значения нужно пересчитать.

## 3. Архитектура и подключение

Grafana выполняет SQL непосредственно в существующей `supply_lab`. Отдельный API, ETL и дополнительная БД не нужны. Источник PostgreSQL доступен в Grafana без отдельной установки плагина: [документация источника](https://grafana.com/docs/grafana/latest/datasources/postgres/).

Для согласованности с окружением `lr1` использовать Podman: описать Grafana в `lr10/docker-compose.yaml` и запускать через `podman compose`. Требуется установленный Compose provider. Подключить существующий `lr1-postgres` и Grafana к общей внешней сети `supply-lab`; PostgreSQL повторно не создавать. Версию образа Grafana зафиксировать точным тегом при реализации и записать в README.

| Параметр | Решение |
| --- | --- |
| Интерфейс Grafana | `http://localhost:3000`, публикация только на `127.0.0.1` |
| Данные Grafana | Именованный volume на `/var/lib/grafana` |
| Источник | PostgreSQL, имя `Supply Lab`, стабильный UID `supply-lab-postgres` |
| Адрес из Grafana | `lr1-postgres:5432` в общей контейнерной сети |
| База | `supply_lab` |
| Пользователь | Отдельная роль `grafana_reader` |
| TLS/SSL | `disable` для локального учебного стенда согласно заданию |
| Версия PostgreSQL | 17; удовлетворяет требованию задания 12+ |
| TimescaleDB | Отключён |

`localhost` внутри контейнера Grafana указывает на саму Grafana. Адрес `127.0.0.1:55432` применяется при подключении к PostgreSQL с хоста, но не заменяет адрес контейнера в источнике данных.

Роли `grafana_reader` выдать `CONNECT` на `supply_lab`, `USAGE` на схему `public` и `SELECT` на `deliveries`, `suppliers`, `products`, `warehouses`. Не выдавать права изменения данных. Подключаться суперпользователем из Grafana не требуется. Такой подход соответствует [рекомендациям настройки PostgreSQL](https://grafana.com/docs/grafana/latest/datasources/postgres/configure/).

Пароли Grafana и роли БД передавать через локальный `.env`, исключённый из контроля версий; в `.env.example` оставить только имена переменных и примеры без действующих секретов. Пароль источника передавать через `secureJsonData`. Источник и дашборд загружать из файлов provisioning с постоянными UID: [документация provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/).

## 4. Определения показателей

- **Количество поставок**: `COUNT(*)`, без суммирования количества разнородных товаров.
- **Стоимость партий**: `SUM(quantity * unit_cost)` по всем статусам. Это стоимость зарегистрированных партий, а не оплаченные закупки или выручка.
- **Доля отклонённых**: `100.0 * COUNT(*) FILTER (WHERE quality_status = 'rejected') / NULLIF(COUNT(*), 0)`.
- **Поставки по дням**: число строк `deliveries` в каждом календарном дне, отдельно по трём статусам.
- **Топ складов**: десять складов с максимальной стоимостью партий за выбранный период.

Использовать фактическую `deliveries.unit_cost`, а не текущую справочную `products.unit_price`. Валюта в схеме не указана: отображать стоимость в условных денежных единицах, с двумя знаками после запятой, без символа рубля или другой валюты. Сопоставимость денежных значений в одной условной единице является допущением учебной аналитики.

Не суммировать `quantity` между товарами с разными `products.unit`. Не вычислять остатки, прибыль и заполненность складов: необходимых данных о расходе и размещении партий нет. `warehouse_sections` не соединять с поставками: прямой связи с секцией нет, а соединение только по складу размножит строки и завысит агрегаты.

## 5. Период и переменные

Начальный диапазон дашборда: `2025-01-01 00:00:00` — `2026-09-05 00:00:00`. Автообновление отключить, оставить ручное обновление и выбор периода.

Для учебного стенда договориться интерпретировать значения `delivered_at` как UTC без изменения самих данных. Зафиксировать UTC для сессий роли `grafana_reader` и дашборда. Это техническое допущение: исходная БД не содержит часового пояса события, поэтому реальную временную зону складов восстановить нельзя.

Добавить Query-переменную `warehouse`, одиночный выбор. Первая строка — «Все склады», значение `-1`; остальные строки возвращают уникальный код и имя склада. Стандартные Multi-value и Include All отключить, значение по умолчанию — `-1`.

```sql
SELECT label AS __text, value AS __value
FROM (
    SELECT 'Все склады'::text AS label, '-1'::text AS value, 0 AS ordering
    UNION ALL
    SELECT code || ' — ' || name, warehouse_id::text, 1
    FROM public.warehouses
) AS options
ORDER BY ordering, label;
```

Формат `__text` / `__value` позволяет показывать название, передавая идентификатор: [переменные PostgreSQL](https://grafana.com/docs/grafana/latest/datasources/postgres/template-variables/). Значение `-1` зарезервировать для общего просмотра и проверить его отсутствие среди реальных идентификаторов.

Каждый запрос панели должен содержать одинаковый фильтр:

```sql
WHERE $__timeFilter(d.delivered_at)
  AND (
      ${warehouse:sqlstring} = '-1'
      OR d.warehouse_id = CAST(${warehouse:sqlstring} AS bigint)
  )
```

Макрос времени раскрывается Grafana; такой SQL нельзя непосредственно запускать через `psql`. Для независимой проверки заменить макрос конкретными границами периода, переменную — выбранным значением. Для временного ряда вернуть поле `time` и отсортировать его по возрастанию: [редактор запросов PostgreSQL](https://grafana.com/docs/grafana/latest/datasources/postgres/query-editor/).

## 6. Состав дашборда

| № | Панель | Тип Grafana | Данные и отображение |
| --- | --- | --- | --- |
| 1 | Количество поставок | Stat | `COUNT(*)`, целое число |
| 2 | Стоимость партий | Stat | Сумма `quantity * unit_cost`, два десятичных знака |
| 3 | Доля отклонённых поставок | Stat | Процент от 0 до 100, два десятичных знака |
| 4 | Поставки по дням и статусам | Time series | Три линии: принято, на проверке, отклонено |
| 5 | Топ-10 складов по стоимости партий | Bar chart | Горизонтальные столбцы; подпись `code — name` |
| 6 | Последние поставки за период | Table | До 100 последних строк с деталями поставок |

Размещение в сетке Grafana из 24 колонок: панели 1–3 по 8 колонок в первом ряду, панели 4–5 по 12 во втором, панель 6 на всю ширину в третьем. Название и описание дашборда должны объяснять, что стоимость включает все статусы. Цвета статусов едины: зелёный — принято, жёлтый — проверка, красный — отклонено.

### Контракт запросов

Панели 1–3 используют `FROM public.deliveries d` и общий фильтр из раздела 5. Выражения результата:

```sql
-- Панель 1
COUNT(*) AS delivery_count

-- Панель 2
COALESCE(SUM(d.quantity * d.unit_cost), 0) AS total_cost

-- Панель 3
100.0 * COUNT(*) FILTER (WHERE d.quality_status = 'rejected')
    / NULLIF(COUNT(*), 0) AS rejected_percent
```

Это фрагменты SELECT, а не самостоятельные SQL-команды. Панели 1–3 используют формат Table и выводят одно числовое значение. При пустой выборке количество и стоимость равны нулю; доля равна `NULL` и отображается как «Нет поставок», поскольку процент не определён.

Панель 4 использует `FROM public.deliveries d`, общий фильтр, `GROUP BY 1 ORDER BY 1` и следующие поля SELECT:

```sql
date_trunc('day', d.delivered_at) AT TIME ZONE 'UTC' AS time,
COUNT(*) FILTER (WHERE d.quality_status = 'accepted') AS accepted,
COUNT(*) FILTER (WHERE d.quality_status = 'inspection') AS inspection,
COUNT(*) FILTER (WHERE d.quality_status = 'rejected') AS rejected
```

Формат результата — Time series. Дни без поставок остаются пропусками, соединение пропусков отключено; это поведение пояснить в описании панели. Первая и последняя суточные группы могут охватывать неполный день при произвольном выборе периода.

Панель 5 соединяет `deliveries d JOIN warehouses w ON w.warehouse_id = d.warehouse_id`, применяет общий фильтр, группирует по `w.warehouse_id, w.code, w.name`. Возвращает `w.code || ' — ' || w.name AS warehouse` и `SUM(d.quantity * d.unit_cost) AS total_cost`; сортировка `total_cost DESC, w.warehouse_id`, ограничение `LIMIT 10`. Формат — Table. Топ-10 не обязан суммироваться в общий итог панели 2, поскольку остальные склады исключены.

Панель 6 соединяет `deliveries d` с `suppliers s`, `products p`, `warehouses w` по соответствующим первичным ключам. После общего фильтра сортирует по `d.delivered_at DESC, d.delivery_id DESC`, применяет `LIMIT 100`. Формат — Table. Возвращаемые колонки:

- `d.delivery_id`, `d.delivered_at`, `d.batch_number`.
- `s.name AS supplier`, `p.sku`, `p.name AS product`.
- `w.code AS warehouse_code`, `w.name AS warehouse`.
- `d.quantity`, `p.unit`, `d.unit_cost`, `d.quantity * d.unit_cost AS total_cost`.
- `d.quality_status`, `d.expires_on`.

В таблице перевести статусы через value mappings, отсутствие срока годности показывать как «Не указан». Ограничение в 100 строк указать в названии или описании панели. Фильтр по складу и времени применяется до ограничения строк во всех панелях.

## 8. Порядок реализации и проверки

1. Проверить существующую `supply_lab`: наличие таблиц, число строк и диапазон дат. При отсутствии базы выполнить подготовку по README `lr1`, учитывая фактическую рабочую директорию и пути монтирования. Не перезагружать уже заполненную базу автоматически.
2. Создать роль чтения и проверить успешный SELECT под этой ролью; проверить отсутствие прав INSERT, UPDATE и DELETE через `has_table_privilege`, не изменяя данные.
3. Создать сеть `supply-lab`, подключить к ней `lr1-postgres`, подготовить Compose и provisioning. Проверить конфигурацию командой `podman compose -f lr10/docker-compose.yaml config` из корня проекта. Вывод с подставленными секретами не сохранять в отчёт.
4. Запустить Grafana командой `podman compose -f lr10/docker-compose.yaml up -d`. Открыть источник `Supply Lab`, выполнить Save & Test, зафиксировать успешное соединение.
5. Реализовать шесть панелей и проверить каждую на полном периоде. Подставить границы периода и выбранный склад в контрольные SQL-запросы, сравнить результаты с Grafana.
6. Выбрать один склад с поставками: все шесть панелей должны показывать только его данные. Изменить период и проверить согласованность итогов и строк таблицы. Проверить период без поставок и возврат к «Все склады».
7. Перезапустить Grafana и проверить сохранение источника, UID дашборда, начального периода и переменной. Сохранить скриншоты и инструкцию воспроизведения.

## 9. Критерии приёмки

- Grafana открывается локально; Save & Test подтверждает соединение с `supply_lab`.
- Дашборд содержит шесть работающих панелей, включая Table, Time series и Bar chart.
- На неизменённых данных CSV при полном периоде и всех складах показатели равны: 5000 поставок, стоимость `280292140666.85`, доля отклонённых `19.46%`.
- Суммы дневных значений по статусам равны 3019, 1008 и 973; их общий итог равен 5000.
- Контрольный SQL подтверждает состав и порядок топ-10 складов, а также 100 последних поставок; соединения со справочниками не увеличивают количество строк поставок.
- Выбор склада и периода согласованно меняет все панели; пустые выборки не вызывают SQL-ошибок или деления на ноль.
- Денежные значения не объявляются выручкой; количества разных единиц измерения не складываются; часовой пояс задан явно.
- После перезапуска Grafana дашборд восстанавливается из сохранённых файлов; в репозитории нет действующих паролей.
- README и скриншоты позволяют воспроизвести и продемонстрировать результат лабораторной работы.
