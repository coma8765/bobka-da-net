# RFC: адаптация LINQ-задания на Python и SQLAlchemy для ЛР № 7

## Статус

Предлагается к реализации.

Основание: [задание лабораторной работы](task.pdf).

## 1. Контекст и адаптация технологии

Исходное задание сформулировано для LINQ - технологии платформы .NET.
Проект использует Python и PostgreSQL, поэтому буквальный LINQ неприменим.
Согласно `NOTES.md`, допустим SQLAlchemy. В работе сохраняются три требуемых
уровня обработки:

- LINQ to Object заменяется запросами к коллекциям Python-объектов;
- LINQ to XML/JSON заменяется операциями стандартного модуля `json`;
- LINQ to SQL заменяется SQLAlchemy ORM и SQL Expression Language.

Адаптация должна показать те же идеи: фильтрацию, проекцию, сортировку,
группировку, соединение, чтение и изменение документа, а также запросы и DML,
которые транслируются в SQL.

## 2. Ограничения

- СУБД - PostgreSQL 17, база `supply_lab` из `lr1`.
- Python-клиент - SQLAlchemy 2.x с драйвером Psycopg 3.
- Прикладные запросы строятся ORM/API SQLAlchemy. Raw SQL разрешён только для
  `CALL`, поскольку вызов процедуры является самостоятельным требованием.
- Модели исходных таблиц отображают существующую схему `public` и не создают
  её через `metadata.create_all()`.
- Собственная таблица ЛР 7 создаётся отдельным SQL-сценарием в схеме `lr7`.
- Сеанс SQLAlchemy имеет `autoflush=False`, `expire_on_commit=False`; границы
  транзакций задаются явно через `Session.begin()`.
- JSON хранится в UTF-8. Даты, `Decimal` и перечислимые статусы
  сериализуются явными функциями, без `default=str` для всех неизвестных
  типов.

## 3. Модель данных

В `models.py` объявляются `Supplier`, `Product`, `Warehouse`, `Delivery` и
`DeliveryTag` через `DeclarativeBase`.

Первые четыре класса отображают существующие таблицы `public` с их первичными
и внешними ключами. Для `Delivery` задаются отношения `supplier`, `product` и
`warehouse`. Изменение или автоматическое пересоздание таблиц `lr1`
запрещено.

Собственная таблица для безопасной демонстрации DML:

```sql
CREATE SCHEMA IF NOT EXISTS lr7;

CREATE TABLE IF NOT EXISTS lr7.delivery_tags (
    tag_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    delivery_id bigint NOT NULL
        REFERENCES public.deliveries (delivery_id) ON DELETE CASCADE,
    tag varchar(40) NOT NULL CHECK (btrim(tag) <> ''),
    created_at timestamp with time zone NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT delivery_tags_uq UNIQUE (delivery_id, tag)
);
```

## 4. Запросы к коллекции объектов

`object_queries.py` получает обычные списки объектов или dataclass-снимков и
не обращается к базе. Реализуются не менее пяти запросов.

### 4.1. Фильтрация и проекция

Из списка поставщиков выбираются активные с рейтингом не ниже порога, после
чего возвращаются пары `(tax_id, name)`.

### 4.2. Сортировка и ограничение

Товары сортируются по убыванию `unit_price`, затем по `sku`; возвращаются
первые N элементов.

### 4.3. Группировка и агрегирование

Поставки группируются по `quality_status`. Для каждой группы рассчитываются
число строк, суммарное количество и стоимость.

### 4.4. Соединение двух коллекций

Списки поставок и складов соединяются в памяти по `warehouse_id`, результат
содержит `delivery_id`, код склада и город.

### 4.5. Кванторы и вложенная выборка

Для каждого поставщика проверяются `any` поставок со статусом `rejected` и
`all` положительных количеств. Возвращаются поставщики, у которых есть хотя бы
одна поставка и все количества корректны.

Эти пять функций вместе покрывают аналоги `where`, `select`, `orderby`,
`group`, `join`, `any`, `all` и агрегирования LINQ. Входные коллекции не
изменяются.

## 5. Работа с JSON-документом

`json_queries.py` формирует `lr7/data/deliveries.json` из результата одного
SQLAlchemy `select` с соединением поставок, поставщиков, товаров и складов.
Корневой объект имеет версию формата и массив `deliveries`:

```json
{
  "schema_version": 1,
  "generated_at": "2026-09-12T12:00:00Z",
  "deliveries": [
    {
      "delivery_id": 1,
      "supplier": {"tax_id": "770000000001", "name": "Поставщик"},
      "product": {"sku": "SKU-000001", "name": "Товар"},
      "warehouse": {"code": "WH-0001", "city": "Москва"},
      "quantity": 25,
      "unit_cost": "110.50",
      "quality_status": "accepted",
      "tags": []
    }
  ]
}
```

Реализуются три обязательные операции:

1. `read_json(path, status)` читает документ и возвращает проекцию поставок с
   выбранным статусом, отсортированную по `delivery_id`.
2. `update_json(path, delivery_id, status)` меняет `quality_status` ровно у
   одного существующего элемента. Неизвестный ID и недопустимый статус дают
   ошибку без изменения файла.
3. `append_json(path, delivery)` добавляет элемент после проверки уникальности
   `delivery_id` и обязательных полей.

Изменение файла выполняется атомарно: новый JSON записывается во временный
файл в том же каталоге, проверяется повторным чтением и заменяет исходный через
`os.replace`.

## 6. Запросы к PostgreSQL через SQLAlchemy

### 6.1. Однотабличная выборка

`select_products(category, min_price, limit)` строит `select(Product)` с
фильтром по категории и цене, сортировкой и ограничением. Все параметры
связываются SQLAlchemy.

### 6.2. Многотабличная выборка

`select_delivery_details(date_from, date_to)` соединяет `Delivery`,
`Supplier`, `Product` и `Warehouse`, вычисляет стоимость как
`quantity * unit_cost` и фильтрует полуинтервал дат.

### 6.3. INSERT, UPDATE и DELETE

Три функции работают с `lr7.delivery_tags`:

- `insert_delivery_tag(delivery_id, tag)` создаёт тег и возвращает `tag_id`;
- `rename_delivery_tag(tag_id, new_tag)` обновляет ровно одну строку;
- `delete_delivery_tag(tag_id)` удаляет ровно одну строку.

Нулевое или множественное число изменённых строк считается нарушением
контракта. Все три операции выполняются в транзакциях и используют выражения
`insert`, `update`, `delete`, а не текстовый SQL.

### 6.4. Доступ только через хранимую процедуру

`describe_table_via_procedure(table_name)` не выполняет предварительных
`SELECT` и получает результат единственным вызовом:

```python
session.execute(
    text("CALL public.sp_describe_table(:table_name, NULL::jsonb)"),
    {"table_name": table_name},
)
```

Используется процедура из ЛР 3. Возвращённый `INOUT`-параметр преобразуется в
словарь и отдаётся вызывающему коду.

```bash
python3 -m lr7.src.demo
python3 -m unittest discover -s lr7/tests
```

## 8. Тестирование

### 8.1. Объекты

Тесты используют небольшие коллекции dataclass-объектов и проверяют пять
запросов, пустые входы, устойчивую сортировку и отсутствие изменения входных
списков. База для этих тестов не нужна.

### 8.2. JSON

Каждый тест работает с копией фикстуры во временном каталоге. Проверяются
чтение, успешное обновление, добавление, отказ для повторного ID,
недопустимого статуса и повреждённого JSON. После ошибки байты исходного файла
должны остаться прежними.

### 8.3. SQLAlchemy

Интеграционные тесты работают в транзакции с итоговым откатом и проверяют:

- скомпилированный однотабличный запрос и его результат;
- корректность полей многотабличного соединения;
- полный цикл insert-update-delete для одного тега;
- откат дубликата `(delivery_id, tag)`;
- получение описания `public.deliveries` только через процедуру ЛР 3;
- отсутствие DDL над таблицами `public` при импорте моделей.

Для диагностической проверки SQL включается `echo` только через переменную
`LR7_SQL_ECHO=1`; в обычном режиме запросы не засоряют вывод.

## 9. Критерии готовности

1. Реализованы пять запросов к коллекциям с полным набором требуемых операций.
2. JSON-документ создаётся из БД, читается, обновляется и дополняется атомарно.
3. ORM-модели соответствуют существующей схеме `supply_lab`.
4. Выполнены однотабличная и многотабличная выборки, DML-набор и доступ через
   процедуру.
5. Raw SQL отсутствует во всех операциях, кроме параметризованного `CALL`.
6. Все модульные и интеграционные тесты проходят и не оставляют данных.
