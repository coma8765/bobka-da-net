# RFC: сравнение PostgreSQL и Redis-кэша для статистики поставок

Статус: реализуется; уточнения стенда приведены ниже.

## 1. Цель и требования задания

Разработать приложение для БД поставок из ЛР № 1, которое каждые 5 секунд
получает одинаковую статистику двумя способами: непосредственно из PostgreSQL
и через Redis как кэш результата SQL-запроса. Сравнить время выполнения
в четырёх сценариях: без изменений, с добавлением, удалением и обновлением
строк каждые 10 секунд. Сохранить измерения, построить графики и объяснить
полученные различия.

Основание: [задание ЛР № 9](task.pdf),
[описание БД](../../lr1/db/DESC.md) и [README ЛР № 1](../../lr1/README.md).
В запросе указан `taask.pdf`, фактическое имя файла — `task.pdf`.
Схема ниже взята из документации ЛР № 1; SQL-исходники и работающий экземпляр
БД при подготовке RFC не проверялись. При реализации схема сверена с
каталогом PostgreSQL: основная БД содержит 5006 поставок, триггер аудита ЛР4
и документы ЛР5, ссылающиеся на каждую поставку.

Обязательные требования PDF:

- Установить Redis и проверить его доступность.
- Подготовить статистический SQL-запрос на данных существующей БД.
- Реализовать прямое чтение и чтение с кэшированием с периодом 5 секунд.
- Учесть добавление, удаление и изменение данных основной БД.
- Сравнить оба режима для всех четырёх сценариев и построить графики.

Выбор статистики, TTL, длительности прогонов, формата результатов и способа
инвалидации ниже является проектным решением, а не дополнительным условием PDF.

## 2. Исходная модель данных

Используется PostgreSQL и база `supply_lab`. В README указан контейнер
PostgreSQL 17, подключение с хоста через порт `55432`, Python и Psycopg.
Документированный набор содержит по 1000 поставщиков, товаров и складов,
3000 секций и 5000 поставок. Перед экспериментом фактические количества
фиксируются отдельно.

| Таблица | Назначение и значимые поля |
| --- | --- |
| `suppliers` | Поставщики; ключ `supplier_id` |
| `products` | Товары; ключ `product_id`, уникальный `sku`, `name`, `unit`, справочная цена `unit_price` |
| `warehouses` | Склады; ключ `warehouse_id` |
| `warehouse_sections` | Секции склада; `section_id`, `warehouse_id`, рекурсивный `parent_section_id` |
| `deliveries` | Поставки; `delivery_id`, три внешних ключа, `quantity`, `unit_cost`, `delivered_at`, `batch_number`, `quality_status`, `expires_on` |

`deliveries` связывает поставщика, товар и склад. Количество и закупочная цена
положительны. Допустимые статусы: `accepted`, `inspection`, `rejected`.
Комбинация `(supplier_id, product_id, warehouse_id, batch_number)` уникальна.
Идентификаторы генерируются через `IDENTITY`; все поля поставки, кроме
`expires_on`, обязательны. Удаление родительских записей с поставками
ограничено внешними ключами.

Для эксперимента изменяются только строки `deliveries`. Справочники и
иерархия секций сохраняются. Новые таблицы, индексы и миграции для выбранного
запроса не требуются; одинаковая схема применяется в обоих режимах.

## 3. Статистический запрос

Статистика: десять товаров с наибольшей суммарной закупочной стоимостью
принятых поставок за всё время. Это статистика поступлений, а не продаж:
в исходной модели нет заказов покупателей или списаний со склада.

Стоимость считается по исторической цене `deliveries.unit_cost`, а не по
текущей `products.unit_price`. Для сравнения денежных сумм принимается
допущение об общей валюте: отдельного поля валюты в модели нет. Количество
товаров с разными единицами измерения не используется как общая шкала рейтинга.

```sql
SELECT
    p.product_id,
    p.sku,
    p.name,
    COUNT(*) AS delivery_count,
    SUM(d.quantity * d.unit_cost) AS total_cost
FROM public.deliveries AS d
JOIN public.products AS p ON p.product_id = d.product_id
WHERE d.quality_status = 'accepted'
GROUP BY p.product_id, p.sku, p.name
ORDER BY total_cost DESC, p.product_id ASC
LIMIT 10;
```

Вторичная сортировка по `product_id` делает результат однозначным при
равенстве сумм. Если подходящих товаров меньше десяти, возвращаются все;
при отсутствии принятых поставок возвращается пустой список.

Оба режима используют этот SQL без отличий. Результат преобразуется
в упорядоченный список объектов с перечисленными полями. `total_cost`
передаётся строкой с двумя десятичными знаками без преобразования в `float`.
Идентификаторы и количество поставок передаются целыми числами.

## 4. Архитектура приложения

Реализовать консольное приложение на Python с Psycopg, redis-py и Matplotlib.
HTTP-сервер и пользовательский интерфейс для выполнения задания не нужны.
Версии зависимостей фиксируются при реализации и записываются в метаданные
эксперимента.

| Компонент | Ответственность |
| --- | --- |
| Репозиторий PostgreSQL | Статистический SQL, преобразование результата, транзакции изменения поставок |
| Сервис статистики | Выбор режима `direct` или `cached`, чтение и заполнение кэша |
| Генератор изменений | Детерминированные `INSERT`, `DELETE`, `UPDATE` с периодом 10 секунд |
| Исполнитель эксперимента | Расписание, порядок операций, измерение времени, проверка результатов |
| Построение отчёта | Агрегация CSV, графики, сводная таблица |

Параметры подключения задаются через `PGHOST`, `PGPORT`, `PGUSER`,
`PGPASSWORD`, `PGDATABASE`, `REDIS_URL`; пароли не записываются в отчёт.
Подключения открываются до замеров и переиспользуются. Чтения PostgreSQL
выполняются в autocommit, записи — в явных коротких транзакциях.

Каждый прогон имеет отдельный `run_id`, один процесс и последовательный
исполнитель операций. Запись, инвалидация и чтение не выполняются параллельно.
Это исключает гонку, при которой старый результат записывается в кэш уже
после его удаления. Конкурентные процессы записи и произвольные внешние
изменения не входят в гарантии основного эксперимента.

### 4.1. Прямое чтение

При каждом событии чтения выполнить SQL, получить все строки и преобразовать
их в общий формат результата. Redis в этом режиме не используется.

### 4.2. Чтение через Redis

Использовать cache-aside: PostgreSQL остаётся источником данных, а Redis
хранит готовый результат агрегирования.

Ключ: `lr9:<run_id>:stats:top-products-by-cost:v1`.
Значение: UTF-8 JSON-объект с полями `schema_version: 1` и `rows`.
TTL: 3600 секунд, без продления при чтении. Он превышает длительность
прогона и служит для удаления оставшихся ключей, не заменяя инвалидацию.
Версия в ключе изменяется при изменении SQL или формата ответа.

Алгоритм:

1. Выполнить `GET` ключа текущего прогона.
2. При наличии корректного значения разобрать JSON и вернуть `rows` (`hit`).
3. При отсутствии значения выполнить SQL и преобразовать результат (`miss`).
4. Сериализовать ответ и записать его одной командой `SET ... EX 3600`.
5. Вернуть результат в общем формате.

Пустой список является корректным кэшированным результатом. Отсутствие
ключа проверяется отдельно от пустоты списка. Повреждённый JSON или неизвестная
версия считаются промахом, значение заменяется после обращения к PostgreSQL.
Установку значения вместе со сроком жизни поддерживает
[команда Redis SET](https://redis.io/docs/latest/commands/set/).

### 4.3. Изменения и согласованность

В режиме `cached` успешная запись выполняется так:

1. Начать транзакцию PostgreSQL.
2. Выполнить ровно одно изменение строки поставки и проверить число строк.
3. Выполнить `COMMIT`.
4. Удалить ключ статистики через `DEL`.
5. Только затем разрешить следующее чтение.

После rollback удаление ключа не требуется. Инвалидация до commit не
используется. Любое изменение `deliveries` инвалидирует результат, даже если
оно не влияет на топ-10: это упрощает проверку корректности. Если позднее
появится запись в `products`, изменение `name`, `sku` или состава товаров
также должно проходить через этот механизм.

Удаление отсутствующего ключа является штатным случаем:
[команда Redis DEL](https://redis.io/docs/latest/commands/del/).
При недоступности Redis чтение возвращает результат PostgreSQL с признаком
`fallback`. Если `DEL` после commit завершился ошибкой, процесс блокирует
чтение старого ключа до успешного повторного удаления. Подтверждённая запись
PostgreSQL не откатывается и не повторяется из-за ошибки Redis.

Прогон с ошибкой Redis сохраняется для диагностики, но исключается из
основного сравнения производительности. При перезапуске создаётся новый
`run_id`, поэтому старый ключ не используется. При ошибке PostgreSQL
прогон завершается с диагностикой, без выдачи старого кэша как свежих данных.

Это гарантия актуальности после изменений, выполненных данным приложением.
Для сторонних записей немедленное обновление не гарантируется; одного TTL
для этого недостаточно. Триггеры, CDC и распределённая координация в ЛР
не реализуются.

## 5. Окружение и исходные данные

Запустить Redis локально в Podman, как и PostgreSQL из ЛР № 1. Зафиксировать
версию образа и его digest в отчёте; проверить `redis-cli PING`, ожидается
`PONG`. Пример команды запуска после выбора версии:

```bash
podman run --name lr9-redis \
  -p 127.0.0.1:56379:6379 \
  -d "docker.io/library/redis:${REDIS_VERSION}" \
  redis-server --save "" --appendonly no
podman exec lr9-redis redis-cli PING
```

`REDIS_VERSION` необходимо задать явно; адрес для приложения —
`redis://127.0.0.1:56379/0`. Персистентность Redis отключена, поскольку
все данные кэша восстанавливаются SQL-запросом. Установка опирается на
[официальную документацию Redis](https://redis.io/docs/latest/develop/),
куда перенаправляет quickstart из задания.

Эксперименты проводить в отдельной базе `supply_lab_lr9`, созданной из
снимка `supply_lab`. Исходная база ЛР № 1 не изменяется. Снимок включает
схему, данные и состояние sequences. Перед каждым прогоном восстанавливать
одинаковое исходное состояние, проверять ограничения и выполнять `ANALYZE`.
Восстановление и подготовка не входят во время измеряемого запроса.

Уточнение при реализации: после восстановления полного снимка в отдельной
копии очищается `lr5.delivery_documents`, если эта таблица существует.
Иначе её внешний ключ запрещает все удаления поставок. Сам внешний ключ,
схемы, триггер аудита и все данные ЛР1 сохраняются. Подготовка одинакова для
обоих режимов и всех сценариев, выполняется до `ANALYZE` и фиксируется
в метаданных. Таблица документов основной БД не изменяется.

## 6. Методика эксперимента

### 6.1. Матрица запусков

Для каждого сценария выполнить отдельные прогоны `direct` и `cached`.
Каждый прогон длится 300 секунд; выполнить три повтора каждой комбинации.
Итого 24 прогона. Порядок режимов чередовать между повторами.

| Сценарий | Операция каждые 10 секунд | Ожидаемое поведение кэша |
| --- | --- | --- |
| `static` | Нет | Первый запрос — miss, остальные — hit |
| `insert` | Добавление одной принятой поставки | После commit — miss, между записями — hit |
| `delete` | Удаление одной принятой поставки | После commit — miss, между записями — hit |
| `update` | Увеличение количества в одной принятой поставке | После commit — miss, между записями — hit |

Чтения запланированы в моменты `t = 0, 5, ..., 300`: 61 чтение за прогон.
Изменения запланированы в моменты `t = 10, 20, ..., 300`: 30 изменений.
При совпадении времени сначала выполнить запись и инвалидацию, затем чтение.
При отсутствии ошибок и истечения TTL в изменяемых сценариях ожидаются
31 miss и 30 hit; в статическом — 1 miss и 60 hit.

Использовать монотонные часы и абсолютные дедлайны относительно начала
прогона, а не `sleep(5)` после окончания работы. Записывать фактическое
опоздание относительно дедлайна. Если операция не позволяет выдержать
следующее событие расписания, отмечать нарушение; прогон сохранять,
но не включать в основное сравнение с корректными прогонами.

Перед каждым прогоном выполнить пять прямых чтений для одинакового прогрева
PostgreSQL и открыть соединение Redis. Ключ нового прогона должен отсутствовать.
Холодный старт Redis-кэша при `t = 0` включается в измерения и отдельно
помечается в отчёте. Кэш операционной системы и PostgreSQL принудительно
не сбрасывается; сравнение проводится при прогретой основной БД.

### 6.2. Правила генерации изменений

Использовать фиксированный seed и один исходный снимок. Перед каждым
изменением выбирать товар на первом месте текущего рейтинга и его принятую
поставку с минимальным `delivery_id`. Выбор одинаков при одинаковом состоянии
БД и выполняется вне измеряемого чтения в обоих режимах.

- `insert`: скопировать внешние ключи выбранной поставки; задать `quantity = 100`,
  `unit_cost = 100.00`, `quality_status = 'accepted'`, уникальный номер партии
  вида `LR9-I-000001`. Проверить отсутствие таких номеров до запуска.
  `delivery_id` получает БД, `delivered_at` берётся из фиксированного начала
  сценария плюс номер шага по 10 секунд, `expires_on` — из выбранной поставки.
- `delete`: удалить выбранную поставку по `delivery_id`, проверить, что удалена
  одна строка. Родительские справочники не удалять.
- `update`: увеличить `quantity` выбранной поставки на 100; остальные поля
  оставить прежними. Проверить одну изменённую строку и отсутствие переполнения.

Эти операции меняют стоимость текущего лидера, поэтому позволяют проверять
обновление самого результата, а не только факт удаления Redis-ключа.
Перед экспериментом проверить достаточное число принятых поставок для
30 удалений с сохранением хотя бы одной строки, допустимость новых значений
и совместимость копируемых полей с ограничениями БД. При невыполнении
предусловий остановиться до замеров и подготовить корректный снимок.
Каждый сценарий начинается с исходного снимка независимо от остальных.

### 6.3. Границы измерения и проверка результата

Основная метрика — время вызова получения статистики через
`time.perf_counter_ns()`, переведённое в миллисекунды:

- `direct`: выполнение SQL, получение строк и преобразование общего результата;
- `cached/hit`: Redis GET, разбор и проверка JSON, получение общего результата;
- `cached/miss`: Redis GET, SQL, преобразование, сериализация и Redis SET.

Соединения, ожидание расписания, операции записи, инвалидация, запись CSV,
печать и построение графиков находятся вне этого интервала. Время транзакции
изменения и время инвалидации измеряются отдельно. Попадание в кэш не должно
выполнять SQL внутри измеряемого вызова.

Для проверки правильности после каждого измерения выполнить контрольный SQL
вне измеряемого интервала, пока следующая запись ещё не началась. Сравнить
полный нормализованный результат, включая порядок строк и точные суммы.
В обоих режимах контроль выполняется одинаково; он дополнительно прогревает
PostgreSQL, что явно указывается в отчёте. Контрольные запросы учитывать
отдельно от SQL-запросов сервиса статистики. Любое расхождение делает прогон
неуспешным.

### 6.4. Сохраняемые результаты

Для каждого прогона создать каталог `lr9/results/<run_id>/`:

| Файл | Содержимое |
| --- | --- |
| `metadata.json` | Сценарий, режим, повтор, seed, периоды, TTL, версии, digest образов, описание машины, число строк, идентификатор снимка и версия SQL |
| `measurements.csv` | Номер чтения, плановое и фактическое время, опоздание, `latency_ms`, `cache_status`, число строк результата, признак равенства контрольному SQL, ошибка |
| `mutations.csv` | Номер операции, её время, вид, `delivery_id`, число затронутых строк, время транзакции, время и статус инвалидации |

В `cache_status` использовать значения `bypass`, `hit`, `miss`, `fallback`.
Ошибки записывать явно; не подменять их нулевой длительностью.
Сводный отчёт и графики сохранять в `lr9/results/summary/`.

## 7. Анализ и графики

Построить четыре графика «время выполнения запроса от времени эксперимента»,
по одному на сценарий. По оси X — секунды от начала, по оси Y — миллисекунды.
На каждом графике показать `direct` и `cached`, выделить hit/miss и моменты
изменений. Для трёх повторов использовать отдельные панели, сохраняя
сопоставимый масштаб. Сохранить PNG и исходные CSV.

Подготовить сводную таблицу по сценарию, режиму и повтору: количество чтений,
mean, median, p95, min, max, hit rate, число SQL-вызовов сервиса, число ошибок
и расхождений с контрольным результатом. Дополнительно разделить длительности
`cached` на hit и miss. Указать способ вычисления p95, например nearest-rank.

Ускорение рассчитывать как `mean(direct) / mean(cached)` для соответствующего
сценария и повтора, включая промахи. Отдельное сравнение direct с hit является
дополнительной метрикой. В отчёте объяснить стоимость заполнения кэша и
уменьшение hit rate из-за изменений.

Не задавать обязательный коэффициент ускорения: на документированных
5000 поставок SQL может оказаться достаточно быстрым, а Redis добавляет
сетевой обмен и сериализацию. Отрицательное ускорение является допустимым
результатом. Увеличенный набор данных можно исследовать отдельно, сохранив
основное сравнение на исходном объёме и не смешивая результаты.

## 9. Проверка и критерии готовности

До длительных прогонов проверить публичные операции приложения на небольшой
контролируемой БД и отдельном Redis namespace:

- SQL учитывает только `accepted`, корректно считает суммы, ограничивает
  результат десятью строками и стабильно разрешает равенство сумм.
- Первое чтение даёт miss, повторное — hit с тем же результатом без SQL
  в сервисе статистики. Пустой список также кэшируется.
- После каждой из трёх операций и commit следующее чтение даёт miss
  и совпадает с контрольным SQL; rollback сохраняет прежний результат.
- Истечение TTL, отсутствие ключа и повреждённый JSON приводят к пересчёту.
- Ошибка Redis не выдаёт устаревший результат; ошибка DEL блокирует
  использование старого ключа и не приводит к повторной записи в PostgreSQL.
- При совпадении дедлайнов изменение предшествует чтению; задержки
  регистрируются. Быстрые проверки расписания используют управляемые часы.
- Восстановление снимка возвращает одинаковые данные и состояние sequences
  перед обоими режимами.

Лабораторная работа готова, когда Redis отвечает на PING, приложение выполняет
оба режима, все 24 корректных прогона завершены без расхождений результатов,
сохранены сырые измерения и четыре сравнительных графика, а отчёт содержит
сводные показатели, условия воспроизведения и выводы по всем четырём сценариям.
Состояние реализации и проверок фиксируется в [RFC-track.md](RFC-track.md).
Короткие проверочные измерения публикуются отдельно от полного эксперимента;
их длительность явно указывается в отчёте.
