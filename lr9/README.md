# Лабораторная работа № 9: PostgreSQL и Redis

Приложение сравнивает прямой SQL и Redis-кэш для топ-10 товаров по стоимости
принятых поставок. Каждые 5 секунд получает статистику, каждые 10 секунд
меняет одну поставку в сценариях `insert`, `delete`, `update`.
В сценарии `static` данные не меняются.

Описание решений: [RFC](docs/RFC.md). Фактические проверочные измерения:
[отчёт](docs/report.md). Полные данные каждого запуска сохраняются в `results`.

## Подготовка

Команды ниже выполняются из `lr9`. Требуются Python 3.13 или новее, Podman,
работающий контейнер PostgreSQL из ЛР1 и база `supply_lab`.

```bash
cd lr9
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
podman machine start
podman start lr1-postgres
podman run --name lr9-redis \
  -p 127.0.0.1:56379:6379 \
  -d docker.io/library/redis:7.4-alpine \
  redis-server --save '' --appendonly no
podman exec lr9-redis redis-cli PING
```

Если машина уже запущена, `podman machine start` пропускается. Для существующего
контейнера Redis использовать `podman start lr9-redis` вместо `podman run`.
Ответ проверки Redis должен быть `PONG`. При выполнении использован Redis
из ветки 7.4; точные версия и digest образа записываются в метаданные.

Для установки только рабочих зависимостей достаточно `requirements.txt`.
Все непосредственные зависимости закреплены; `requirements-lock.txt`
содержит также версии транзитивных зависимостей проверенного окружения.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PGHOST` | `127.0.0.1` | Адрес PostgreSQL с хоста |
| `PGPORT` | `55432` | Порт PostgreSQL с хоста |
| `PGUSER` | `postgres` | Пользователь локального лабораторного стенда |
| `PGPASSWORD` | `postgres` | Пароль PostgreSQL |
| `PGDATABASE` | `supply_lab_lr9` | Отдельная экспериментальная БД |
| `LR9_SOURCE_DATABASE` | `supply_lab` | База для создания снимка |
| `REDIS_URL` | `redis://127.0.0.1:56379/0` | Подключение Redis |
| `LR9_POSTGRES_CONTAINER` | `lr1-postgres` | Контейнер с `pg_dump` и `pg_restore` |
| `LR9_REDIS_CONTAINER` | `lr9-redis` | Контейнер для фиксации digest Redis |

## Снимок и изоляция

```bash
.venv/bin/python -m src snapshot
```

Команда читает `supply_lab`, создаёт `snapshots/baseline.dump` и JSON с SHA-256.
Повторное создание по тому же пути отклоняется. Для нового снимка передать
`--snapshot snapshots/new-baseline.dump`, затем указывать этот путь при запуске.
Снимки исключены из системы контроля версий; их нужно сохранять отдельно для
точного воспроизведения опубликованных измерений.

Каждый `run` и каждый элемент `matrix` автоматически восстанавливает снимок
в `supply_lab_lr9`. Повторно пересоздаётся только БД с установленной приложением
меткой `Managed by LR9 benchmark; disposable copy`. Имя ограничено
`supply_lab_lr9` и `supply_lab_lr9_<suffix>`. Исходная БД защищена от выбора
в качестве экспериментальной. Активные сторонние подключения не завершаются
принудительно; они могут помешать пересозданию копии.

Подготовка экспериментальной копии включает очистку `lr5.delivery_documents`,
если таблица существует: в текущем наборе ЛР5 связывает документы со всеми
поставками и запрещает их удаление. Данные пяти таблиц ЛР1, sequences,
триггеры и ограничения сохраняются. В исходной БД документы не удаляются.
Перед измерениями выполняются `ANALYZE` и пять прогревочных SQL.

До начала матрицы приложение пробует все запланированные изменения в
транзакции с rollback, проверяя совместимость с FK и триггерами. После этого
снимок восстанавливается заново, включая состояние sequences. Одновременно
два процесса приложения не могут использовать одну экспериментальную БД:
применяется advisory lock. Произвольные внешние записи в копию не допускаются.

Восстановить копию без запуска эксперимента:

```bash
.venv/bin/python -m src restore
```

## Запуск экспериментов

Один полный прогон, 300 секунд:

```bash
.venv/bin/python -m src run --mode cached --scenario update
```

Доступные режимы: `direct`, `cached`; сценарии: `static`, `insert`, `delete`,
`update`. Каждый прогон содержит чтение в момент 0 и на последнем дедлайне.
При совпадении дедлайнов запись и инвалидация выполняются до чтения.

Полная матрица RFC: 4 сценария × 2 режима × 3 повтора × 300 секунд,
около двух часов плюс подготовка:

```bash
.venv/bin/python -m src matrix --output results/full
.venv/bin/python -m src plot --output results/full --report docs/report.md
```

Для матрицы требуется новый или пустой каталог результатов. При повторном
запуске указать новый `--output`. Это предотвращает смешивание повторов.
Порядок `direct`/`cached` чередуется между повторами.

Короткая проверка всей матрицы с исходными интервалами, около восьми минут:

```bash
.venv/bin/python -m src matrix --duration 20 --output results/smoke-new
.venv/bin/python -m src plot --output results/smoke-new --report docs/report.md
```

Можно задать `--duration`, `--read-interval`, `--mutation-interval`, `--ttl`,
`--seed`, для одиночного запуска — `--repeat`, для матрицы — `--repeats`.
Длительность должна быть кратна обоим интервалам, TTL должен её превышать.
Выбор изменяемой поставки детерминирован: текущий лидер и минимальный
`delivery_id`. Случайность не используется; seed записывается для совместимости
с RFC и будущих генераторов.

## Метрики и корректность

Каждый каталог прогона содержит:

- `metadata.json`: параметры, снимок, схема, количества строк, версии,
  образы контейнеров, статус и пригодность прогона для сравнения.
- `measurements.csv`: фактическое и плановое время, опоздание, длительность
  чтения, hit/miss/bypass/fallback, SQL-вызовы и результат контрольной проверки.
- `mutations.csv`: изменённая поставка, время транзакции и инвалидации, ошибки.

Контрольный SQL выполняется после каждого измерения вне его интервала,
до следующей записи. Любое расхождение останавливает прогон. Ошибки Redis
дают fallback в PostgreSQL; после неуспешного DEL старый ключ не читается,
пока удаление не завершится успешно. Неуспешная инвалидация не повторяет
подтверждённую запись в БД. Перезапуск использует новый ключ с новым `run_id`.

Ошибки Redis и пропуск следующего дедлайна из-за слишком долгой операции
делают прогон непригодным для сравнения. Ошибки PostgreSQL останавливают
выполнение. Неполные результаты сохраняются со статусом `failed`, без
подстановки нулевых длительностей. Код возврата не равен нулю при ошибках.

В `summary` находятся четыре PNG, сводный CSV и Markdown-отчёт. Графики
показывают оба режима, hit/miss и моменты изменений, отдельно по повторам.
p95 рассчитывается методом nearest-rank. Ускорение учитывает и попадания,
и промахи. Короткие прогоны явно помечаются как проверочные.

## Проверки

```bash
.venv/bin/ruff check src tests
.venv/bin/ruff format --check src tests
.venv/bin/python -m pytest tests -q
.venv/bin/python -m pytest tests --integration -q
```

Без `--integration` проверяются расписание, границы времени, конфигурация
и расчёт метрик. Интеграционные тесты требуют снимок по стандартному пути,
PostgreSQL и Redis. Они используют отдельную БД `supply_lab_lr9_test` и
уникальные Redis-ключи. Не запускать тесты во время итоговых замеров:
они создают дополнительную нагрузку на тот же сервер PostgreSQL.

## Ограничения

Сервис рассчитан на последовательную работу одного процесса. Все изменения
во время эксперимента проходят через него; внешние записи автоматически
не обнаруживаются. Общая валюта закупочных цен является допущением модели.
На небольшом объёме данных Redis не обязан ускорять средний запрос, особенно
при частой инвалидации. Долговечность кэша не требуется: после потери ключа
результат вычисляется заново.
