# RFC: доработка `supply_lab` для лабораторной работы № 3

## Статус

Предлагается к реализации.

## Контекст

В `lr1` создана база PostgreSQL 17 `supply_lab` с таблицами `suppliers`,
`products`, `warehouses`, `warehouse_sections` и `deliveries`. Существующая
модель уже содержит подходящие данные для SQL-модулей: поставки позволяют
строить расчёты и отчёты, а рекурсивная связь
`warehouse_sections.parent_section_id` позволяет обходить дерево складских
секций.

Для лабораторной работы № 3 требуется разработать и протестировать ровно
10 прикладных модулей:

- четыре функции: скалярную, подставляемую табличную, многооператорную
  табличную и рекурсивную;
- четыре хранимые процедуры: обычную, рекурсивную, с курсором и с доступом к
  метаданным;
- два DML-триггера: `AFTER` и `INSTEAD OF`.

## Решение

Исходные таблицы и данные `lr1` следует оставить без изменений. Доработки
нужно оформить отдельными сценариями `lr3`, которые выполняются после
`lr1/queries/01_create_database_and_tables.sql`,
`lr1/queries/02_add_constraints.sql` и `lr1/queries/03_bulk_load.sql`.

Термины задания приведены к PostgreSQL следующим образом:

- аналог подставляемой табличной функции реализуется как функция
  `LANGUAGE sql` с `RETURNS TABLE` и одним запросом;
- аналог многооператорной табличной функции реализуется как функция
  `LANGUAGE plpgsql` с проверками параметров и `RETURN QUERY`;
- триггеры PostgreSQL вызывают вспомогательные функции с
  `RETURNS trigger`. Эти технические функции не входят в четыре прикладные
  функции задания и считаются частью соответствующих триггеров.

## Функции

### 1. Скалярная функция `fn_delivery_total`

Сигнатура: `fn_delivery_total(p_delivery_id bigint) RETURNS numeric(20, 2)`.

Функция должна найти поставку по идентификатору и вернуть её стоимость как
`quantity * unit_cost`. Для отсутствующего идентификатора функция должна
возбуждать понятное исключение, а не возвращать неоднозначный `NULL`.

### 2. Подставляемая табличная функция `fn_supplier_deliveries`

Сигнатура: `fn_supplier_deliveries(p_supplier_id bigint) RETURNS TABLE (...)`.

Функция на `LANGUAGE sql` должна одним запросом вернуть поставки выбранного
поставщика со столбцами:

- `delivery_id`;
- `product_id`, `product_sku`, `product_name`;
- `warehouse_id`, `warehouse_code`;
- `delivered_at`, `quantity`, `unit_cost`;
- вычисленный `total_cost`;
- `quality_status`, `expires_on`.

Результат должен быть упорядочен по `delivered_at`, затем по `delivery_id`.
Неизвестный поставщик даёт пустой набор строк.

### 3. Многооператорная табличная функция `fn_warehouse_product_summary`

Сигнатура:
`fn_warehouse_product_summary(p_warehouse_id bigint, p_from timestamp, p_to timestamp) RETURNS TABLE (...)`.

Функция на `LANGUAGE plpgsql` должна:

1. проверить существование склада;
2. проверить, что `p_from < p_to`;
3. вернуть агрегаты по товарам за полуинтервал `[p_from, p_to)`:
   `product_id`, `sku`, `product_name`, `delivery_count`, `total_quantity` и
   `total_cost`;
4. упорядочить строки по убыванию `total_cost`, затем по `product_id`.

Именно отдельные проверки и последующий `RETURN QUERY` делают функцию
многооператорной.

### 4. Рекурсивная функция `fn_section_tree`

Сигнатура: `fn_section_tree(p_root_section_id bigint) RETURNS TABLE (...)`.

Функция должна с помощью `WITH RECURSIVE` вернуть корневую секцию и всех её
потомков со столбцами `section_id`, `parent_section_id`, `warehouse_id`,
`code`, `name`, `depth` и `path_ids bigint[]`. Корневая секция имеет глубину
0. Массив `path_ids` используется как путь от корня и как защита от
зацикливания на повреждённых данных. Для отсутствующей корневой секции
функция должна возбуждать исключение.

## Хранимые процедуры

### 5. Обычная процедура `sp_register_delivery`

Процедура должна принимать атрибуты новой поставки и возвращать созданный
`delivery_id` через `INOUT`-параметр. Перед вставкой она должна проверить:

- поставщик существует и имеет `is_active = true`;
- товар и склад существуют;
- для скоропортящегося товара передан `expires_on`, который не раньше даты
  поставки;
- бизнес-ключ поставки не дублирует существующую строку.

Остальные инварианты продолжают обеспечиваться ограничениями `lr1`.

### 6. Рекурсивная процедура `sp_set_section_subtree_active`

Сигнатура:
`sp_set_section_subtree_active(p_root_section_id bigint, p_is_active boolean)`.

Процедура должна рекурсивным CTE найти секцию и всех её потомков, после чего
одним `UPDATE` установить им `is_active = p_is_active`. Обход не должен
выходить за границы склада корневой секции. Для неизвестной секции процедура
должна возбуждать исключение.

### 7. Процедура с курсором `sp_open_expiring_deliveries`

Сигнатура:
`sp_open_expiring_deliveries(p_from date, p_to date, INOUT p_cursor refcursor)`.

Процедура должна проверить диапазон дат и открыть курсор с принятыми
поставками, срок годности которых попадает в интервал `[p_from, p_to]`.
Результат должен содержать идентификаторы и названия поставщика, товара и
склада, номер партии, дату поставки, количество и срок годности. Строки
упорядочиваются по `expires_on`, затем по `delivery_id`.

Вызывать и проверять процедуру необходимо внутри явной транзакции:
`BEGIN`, `CALL`, `FETCH ALL`, `COMMIT` или `ROLLBACK`.

### 8. Процедура доступа к метаданным `sp_describe_table`

Сигнатура:
`sp_describe_table(p_table_name text, INOUT p_metadata jsonb)`.

Процедура должна читать `information_schema.columns`,
`information_schema.table_constraints` и
`information_schema.constraint_column_usage` только для схемы `public` и
вернуть JSON со следующими разделами:

- имя и тип объекта;
- столбцы в порядке `ordinal_position`, включая тип, допустимость `NULL` и
  значение по умолчанию;
- ограничения и участвующие в них столбцы.

Недопустимо собирать SQL конкатенацией пользовательской строки. Для
неизвестной таблицы процедура должна возбуждать исключение.

## DML-триггеры и вспомогательные объекты

### 9. Триггер `trg_warehouse_sections_no_cycle` типа `AFTER`

В `lr1` запрещена только непосредственная самоссылка секции, но возможен цикл
из двух и более секций. Это нужно исправить триггером
`AFTER INSERT OR UPDATE OF warehouse_id, parent_section_id` на таблице
`warehouse_sections`.

Вспомогательная триггерная функция
`tf_warehouse_sections_no_cycle()` должна рекурсивно пройти цепочку родителей
от `NEW.parent_section_id`. Если в цепочке встретился `NEW.section_id`, она
возбуждает исключение, вследствие чего исходная DML-операция откатывается.
Обход должен учитывать `warehouse_id` и хранить посещённые идентификаторы,
чтобы завершаться даже при уже повреждённых данных.

### 10. Триггер `trg_v_delivery_entry_dml` типа `INSTEAD OF`

В PostgreSQL триггер `INSTEAD OF` создаётся на представлении. Поэтому нужно
добавить представление `v_delivery_entry`, которое объединяет `deliveries` со
справочниками и показывает:

- `delivery_id`;
- `supplier_tax_id`, `supplier_name`;
- `product_sku`, `product_name`;
- `warehouse_code`, `warehouse_name`;
- `delivered_at`, `quantity`, `unit_cost`, `batch_number`,
  `quality_status`, `expires_on`.

Триггер `INSTEAD OF INSERT OR UPDATE OR DELETE` должен через вспомогательную
функцию `tf_v_delivery_entry_dml()` преобразовывать DML над представлением в
операции над `deliveries`:

- при `INSERT` находить внешние ключи по уникальным `tax_id`, `sku` и
  `warehouse_code` и возвращать созданный `delivery_id` в `NEW`;
- при `UPDATE` запрещать изменение `delivery_id`, повторно разрешать
  бизнес-идентификаторы в идентификаторы и обновлять базовую строку;
- при `DELETE` удалять базовую строку по `OLD.delivery_id`;
- при неизвестном бизнес-идентификаторе возбуждать исключение.

Ограничения первичных, внешних и бизнес-ключей из `lr1` должны продолжать
работать для операций через представление.

## Структура сценариев

При реализации следует создать:

- `lr3/queries/01_functions.sql` — четыре функции;
- `lr3/queries/02_procedures.sql` — четыре процедуры;
- `lr3/queries/03_triggers.sql` — представление, две вспомогательные
  триггерные функции и два триггера;
- `lr3/queries/04_tests.sql` — воспроизводимые проверки всех десяти модулей;
- `lr3/README.md` — порядок развёртывания и запуска тестов.

Сценарии должны использовать явную схему `public`, завершаться при первой
ошибке через `\set ON_ERROR_STOP on` и допускать повторное выполнение через
`CREATE OR REPLACE` и контролируемое удаление ранее созданных объектов.

## Проверки

`04_tests.sql` должен автоматически проверить как успешные, так и ошибочные
сценарии:

- точный расчёт стоимости существующей поставки и ошибку для неизвестной;
- состав и фильтрацию результатов обеих нерекурсивных табличных функций;
- глубину, путь и принадлежность одному складу в рекурсивной функции;
- успешную регистрацию поставки и отказы для неактивного поставщика,
  неверного срока годности и дубликата бизнес-ключа;
- изменение всех секций поддерева без затрагивания соседних ветвей;
- открытие и чтение курсора внутри транзакции;
- получение метаданных таблицы `deliveries` и отказ для неизвестной таблицы;
- разрешённое изменение дерева секций и откат попытки создать косвенный цикл;
- `INSERT`, `UPDATE` и `DELETE` через `v_delivery_entry` с проверкой результата
  в `deliveries`.

Изменяющие данные проверки должны выполняться в транзакции с итоговым
`ROLLBACK`, чтобы исходный набор данных `lr1` оставался неизменным.

## Критерии готовности

Работа считается выполненной, когда:

1. чистая база `supply_lab` из `lr1` успешно расширяется сценариями `lr3`;
2. реализованы все четыре требуемых вида функций и все четыре вида процедур;
3. созданы и реально срабатывают триггеры `AFTER` и `INSTEAD OF`;
4. тестовый сценарий проверяет каждый из десяти модулей и ожидаемые ошибки;
5. после тестов исходные строки `lr1` не изменены;
6. повторный запуск сценариев не оставляет конфликтующих объектов.
